# 0node facade writing pattern

A reusable editorial pattern for this README family. This is repository documentation, not an installed Codex artifact-template skill.

## Voice

Write like someone who can see the bridge everyone is forced to cross and intends to build another. The ambition belongs in the purpose. Present-tense capability claims belong to inspected source and named evidence. Make explanations generous and sentences sharp.

## Shape

1. **Name + one strike.** A short, distinct promise about the problem. No badge wall or stack list before the reader knows why to care.
2. **The ordinary scene.** A bridge, a queue, a lost note, a sleeping laptop, a question typed on a phone. Explain the component through a consequence someone can recognize.
3. **The mechanism.** Topology: what can reach what. Geometry: a chosen way to measure position, distance or cost. Flow: what moves through the available connections, with capacity and permission constraints. Clarify when this is a design analogy rather than implemented graph machinery.
4. **The working entrance.** Name what the current branch contains. Link to actual source, contracts, build instructions or a bounded local command. Put unresolved prerequisites beside the command that depends on them.
5. **The horizon.** State the next intended capability without pretending it shipped. Preserve branch, integration, execution and hardware qualification boundaries.
6. **The neighbors.** Link only to verified family repositories and state each relationship in one sentence.

## Example, then abstraction

An illustrative town has two bridges. A 4-unit bridge and a 3-unit bridge can carry 7 units of traffic in total if their access roads do not impose a smaller limit. A 5-unit demand can split 4+1. If the 4-unit bridge closes, only 3 units remain and at least 2 must wait or be refused unless another real path exists. Relabeling the map cannot create capacity.

Topology reveals the crossings. Geometry or chosen cost metrics help compare the paths. Flow reveals who actually gets through. In packet networks, additional latency, ordering, policy and endpoint constraints still matter. This example is arithmetic, not a Blueshoes benchmark or implemented solver claim.

## Avoid

- Status prose that requires hunting through a manifesto to discover a prototype.
- Mathematical decoration without variables or an ordinary explanation.
- Consensus presented as truth, a hash as proof of meaning, a diagram as integration, or a successful build as hardware qualification.
- Universal invisibility, guaranteed censorship bypass, perfect data erasure or automatic safety.
- Describing a feature from an open PR as part of main.
- False live-service, release, package-registry or build claims.
- Mockery of beginners, poverty or the reader's intelligence.

## Pre-publication checks

Read the facade aloud. Confirm that its opening identifies the product, its example teaches something, and its nearest source link supports the claim beside it. Check local links and anchors, preserve useful commands, and review the complete diff. Record only verification actually performed.
